# Ethereum CROPS and Walkaway Review

This review maps the Ethereum implementation to the [official Ethereum Foundation Mandate PDF](https://ethereum.foundation/ef-mandate.pdf), whose technical pillar treats censorship resistance, open source, privacy, and security as an indivisible set and calls for intermediary minimization, structural decentralization, and a credible walkaway path.

This is an engineering alignment review, not Ethereum Foundation certification or endorsement. The implementation does not justify a claim of “100% decentralized”: plan controllers choose future terms, fixed attester majorities decide private claims, eligibility and medical evidence remain offchain, and users still depend on Ethereum access plus the selected ERC-20 contract.

## Walkaway properties

A Nakama operator can disappear without taking custody control with them. Deployed bytecode and state remain on Ethereum; holders can submit claims; expired initial rounds resolve permissionlessly to denial; mature provisional or challenged claims can be finalized; contributors can withdraw only unencumbered equity; approved obligations can be reserved and settled by anyone; unused coverage can expire; and any client can use the canonical ABIs through an independent RPC or local node. No Nakama API, database, frontend, indexer, relayer, deployment key, or factory authority is required for those paths.

The claim adjudication walkaway is deliberately narrower than trustlessness. Attesters are fixed when a plan is created and cannot be replaced. Their disappearance cannot trap a claim or reserve forever because the initial round times out to denial and a challenge round falls back to its initial decision, but an inactive set cannot approve a valid benefit. A later protocol version could use opt-in plural attestation markets, cryptoeconomic availability rules, or privacy-preserving proofs, but that requires a separate threat model and cannot be implied by this release.

## Trust and failure boundaries

- **Factory.** The factory has no owner or mutator after its constructor. Release integrity depends on approving its exact initcode, deriving registry/core CREATE addresses, checking all cross-getters, and verifying every live runtime rather than trusting internal-transaction metadata.
- **Domain and plan controllers.** Controllers can configure or stop future scope-local activity, but cannot seize vault assets, fabricate payout obligations, rewrite existing series or claims, override attesters, or stop vested exits and settlement.
- **Plan attesters.** A strict majority decides exact claim outcomes. A colluding majority can approve dishonest claims or deny honest ones. An inactive majority causes denial at the initial deadline, preserving accounting liveness while sacrificing benefit liveness.
- **Eligibility publishers.** A nonzero eligibility root determines who may activate a series. A bad root can omit eligible users or include unintended addresses, but it cannot be changed after series creation. A zero root is explicitly permissionless.
- **Claimants.** A holder can open only one active claim against remaining position coverage and can rotate the payout recipient with an EIP-712 signature until settlement. Claimants cannot enlarge coverage, choose attesters, duplicate a nullifier, or bypass reserve accounting.
- **Premium payers and contributors.** A premium exists only as part of an atomic position activation and is immediately credited to that series' claims-paying line; arbitrary addresses cannot create standalone premium records. On a `Backstop` line it accrues to existing shareholders, and activation requires live shares. On `SponsorBudget` or `Subsidy` it becomes an irrevocable communal claims reserve. Contributors bear series, claim, token, and attester risk, and can exit only against equity free of open exposure, pending claims, and owed claims.
- **Wiped funding lines.** Ordinary share-minting deposits stop while zero-equity shares remain because accepting them would dilute existing contributors. Attributed no-share earnings may restore an active line within its normal cap; otherwise a new line or series is required.
- **ERC-20 issuers.** Token contracts retain their own freezing, minting, blacklist, governance, and upgrade risk. The protocol rejects non-exact transfer behavior but cannot make a centralized asset decentralized.
- **Ethereum infrastructure.** Ethereum supplies ordering, execution, and data availability. Users should retain an independent RPC or local-node path rather than treating one hosted provider as mandatory.
- **Offchain health systems.** Medical evidence, identity verification, eligibility-list construction, notifications, and user interfaces remain offchain. The protocol commits to public state transitions and reserve consequences; it does not make private health data public or eliminate every service dependency.

## Mainnet release conditions

Do not describe this implementation as mainnet-ready or fully decentralized until all of the following are true:

1. An independent smart-contract audit is complete, findings are resolved or explicitly accepted, and its SHA-256 digest is bound into the reviewed release manifest.
2. The exact source commit has a clean production build, fresh four-contract artifact and ABIs, EIP-170 runtime margin for every contract, EIP-3860 initcode margin for the factory and templates, final adversarial test evidence, and a public testnet soak using every supported production token behavior.
3. Immutable-deployment risk, fixed-attester approval risk, eligibility-root governance, ERC-20 issuer risk, public metadata, privacy limits, and lack of privileged recovery are disclosed before users fund or activate a series.
4. The single factory transaction is sent by the approved signer only after the no-transaction preflight passes, is durably journaled, receives at least 12 confirmations, and remains `deployed-unverified` until promotion independently verifies its canonical finalized block, factory initcode, derived children, mutual bindings, exact live/template hashes, and Sourcify v2 exact creation/runtime matches for factory, core, and registry.
5. Independent clients can reconstruct state and execute every walkaway path without Nakama-hosted infrastructure, using the same four audited ABIs and schema-v3 manifest.
6. The supported token, initial domains, plans, attesters, eligibility roots, immutable series terms, funding lines, signer funding, migration sequence, and incident disclosures receive explicit release approval. No placeholder address or unaudited configuration may enable mainnet writes.

The release tooling fails closed until these conditions are represented by a reviewed operator-local `deployments/ethereum-mainnet.release.json`. That file is ignored so it can bind an already committed source HEAD without a commit-hash self-reference; the tracked example remains `not-approved`. No mainnet transaction is authorized by this document.
